# Контрактные решения MVP

## Владение данными

| Данные | Источник истины | Как обновляются |
| --- | --- | --- |
| Заведение, публичное меню, цена и наличие | Platform, на основе снимка venue | Venue отправляет полный снимок меню с монотонной версией. |
| Внешний идентификатор блюда | Venue | Передаётся в menu sync и сопоставляется с публичным `productId`. |
| Заказ, его цены, адрес и история статусов | Platform | Platform создаёт снимок заказа; customer и venue посылают только допустимые команды. |
| Локальная кухня и `venueOrderId` | Venue | Venue создаёт ID до подтверждения заказа и передаёт его при accept. |

Примерное заведение детерминированно выводит отдельный `venueOrderId` из
`platformOrderId` в собственном namespace и хранит оба значения в локальном
заказе. Поэтому идентификаторы разных систем не совпадают, а повтор journal
после рестарта восстанавливает ту же пару без отдельного координационного
запроса.

При menu sync platform возвращает для каждого блюда пару
`externalItemId → productId`. Venue сохраняет это соответствие и применяет
обратное преобразование к `productId` из событий заказа до записи локальной
кухонной read-модели. Если соответствия нет, событие ставится в локальную
очередь повторов: публичный UUID никогда не подменяет локальный ID блюда, но
одно проблемное событие не блокирует обработку более новых событий.

## Жизненный цикл заказа

```text
pending_confirmation ──venue accept──► accepted ─► preparing ─► ready ─► delivering ─► delivered
         │                                  │
         ├──venue reject──► rejected         └──customer cancel──► cancelled
         └──customer cancel──► cancelled
```

Для каждой команды, меняющей статус, platform блокирует строку заказа через
`SELECT … FOR UPDATE`, проверяет статус уже после захвата блокировки и в одной
транзакции сохраняет снимок заказа, историю статусов, `venueOrderId` (если
есть), событие и idempotency-ответ. При одновременной отмене и старте
приготовления выигрывает первая зафиксированная команда; вторая получает
`409 invalid_order_transition`.

Успешный `Idempotency-Key` хранит снимок ответа этой команды, а не ссылку на
текущий заказ. Поэтому повтор возвращает исходный успешный результат даже
после последующих переходов статуса.

## Доставка изменений заведению

Platform ведёт упорядоченный журнал `order-events` для каждого заведения в
таблице `order_events` PostgreSQL.
Venue читает его polling’ом по непрозрачному cursor и хранит последний
cursor локально. Каждое событие страницы обрабатывается независимо. Временно
неуспешное событие сохраняется в локальной очереди повторов, cursor страницы
продвигается, а следующие события продолжают применяться. При следующем цикле
venue сначала повторяет очередь. После перезапуска in-memory очередь и cursor
сбрасываются, поэтому журнал platform воспроизводится заново. Доставка имеет
семантику *at-least-once*: дубликаты допустимы, поэтому venue применяет событие
идемпотентно по `eventId` и partner-команде с постоянным `Idempotency-Key`.

Снимок применяется только если его `updatedAt` новее локальной read-модели.
Это не позволяет поздно доставленному `created` откатить уже принятый,
отклонённый или отменённый заказ. Новый `pending_confirmation` сохраняется в
локальной очереди заведения без автоматического бизнес-решения. Оператор явно
вызывает локальную команду `accepted` или `rejected`; venue направляет её в
соответствующий partner endpoint и сохраняет локальный результат только после
успешного ответа platform.

Причина отклонения принадлежит каноническому заказу platform, присутствует
только при статусе `rejected` и доставляется venue в каждом соответствующем
journal snapshot. Для остальных status-команд локальный API отклоняет поле
`reason` как `400 invalid_request`.

Так заведение узнаёт и о новых заказах, и об отмене принятого заказа без
непроверяемых callbacks. Снимок заказа сохраняется в событии одновременно с
типом события и стабильным `eventId`.

Ручная смена статуса через API отдельного venue-сервиса также сначала выполняется
в platform.
Только успешный ответ сохраняется локально; при сетевой ошибке состояние venue
остаётся прежним, а постоянный idempotency key делает повтор безопасным.

## Атомарность версии меню

Menu sync блокирует строку заведения и применяет все категории, товары,
mapping и `menu_version` в одной транзакции. Создание заказа перед записью
берёт совместимую блокировку той же строки и повторно сравнивает версию меню.
Поэтому конкурентные menu sync и создание заказа сериализуются: либо заказ
фиксируется на старой версии до публикации снимка, либо получает
`409 menu_version_mismatch` после неё.

## Изоляция заведений

Каждый `X-Venue-API-Key` сопоставляется с активной записью
`venue_api_keys` по SHA-256 fingerprint и даёт ровно один `venueId`. Этот ID
не передаётся в partner-запросе и используется platform как tenant boundary:
синхронизация меню, список заказов, события и любые изменения заказа всегда
выполняются только в рамках аутентифицированного заведения. Заказ другого
заведения отвечает `404 order_not_found`, не раскрывая его существование.

Субъект идемпотентности partner-команд имеет вид `venue:<venueId>`, поэтому
одинаковый `Idempotency-Key` разных заведений не конфликтует.

## Пагинация списков

Каталог заведений и списки заказов используют непрозрачную keyset-пагинацию.
Platform запрашивает `limit + 1` запись и возвращает `nextCursor` только когда
после текущей страницы действительно есть данные. Позиция каталога задаётся
парой `(name, id)` по возрастанию, позиция заказов platform —
`(created_at, id)` по убыванию, а локальных заказов venue —
`(createdAt, venueOrderId)` по убыванию. Поэтому добавление или удаление
записей не приводит к смещению страниц, характерному для `OFFSET`.

Cursor содержит версию формата, тип выдачи, её scope и последнюю позицию.
Scope привязывает его к фильтрам и субъекту: customer cursor нельзя применить
к другому пользователю, partner cursor — к другому заведению или статусу, а
cursor каталога — к другому городу. Повреждённый или несовместимый cursor
возвращает `400 invalid_request`.

## Идемпотентные команды

`POST /api/v1/orders`, отмена заказа и все partner-команды используют
`Idempotency-Key`. Ключ ограничен субъектом и операцией. Повтор того же тела
возвращает ранее зафиксированный результат; тот же ключ с другим телом —
`409 idempotency_key_reused`.
